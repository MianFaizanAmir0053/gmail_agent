# Evaluation data

## Layout

```
data/
  fixtures/                 committed. Anonymised email + hand-written label.
  raw_emails/               GITIGNORED. Real, unredacted mail.
  fixtures_draft/           GITIGNORED. Anonymised, not yet labelled.
  anonymization-map.json    GITIGNORED. Real-identity lookup table.
```

Only `fixtures/` is safe to commit. The other three contain, or can reconstruct, real people's data.

## Adding fixtures from real mail

```powershell
uv run python -m app.eval.fetch --query "meeting OR sync OR call" --max 30
uv run python -m app.eval.anonymize
```

Then, for each file in `fixtures_draft/`: read it, write the `expected` block by hand, wrap it in the fixture envelope (`id`, `tags`, `note`, `now_utc`, `user_timezone`), and move it into `fixtures/`.

Labelling is manual on purpose. A label generated by a model is not a ground truth — it is that model's opinion, and scoring against it measures agreement, not correctness.

## Fixture shape

```json
{
  "id": "fx-001",
  "tags": ["meeting", "relative-date"],
  "note": "why this case exists",
  "now_utc": "2026-08-17T09:00:00Z",
  "user_timezone": "Asia/Karachi",
  "email": { ...EmailMessage... },
  "expected": { ...ExtractionResult... }
}
```

`now_utc` is load-bearing. "Tomorrow" only has a correct answer relative to some instant, so each fixture pins its own. Without it the suite would silently change meaning every day it runs.

## Conventions

Encoded as tests in `tests/test_fixtures.py`, so a fixture that breaks one fails the build.

| Rule | Why |
|---|---|
| Exactly one of `meeting` / `non-meeting` in `tags` | The tag and `expected.is_meeting` must agree, or slices lie |
| `attendees` excludes the account owner (`me@example.com`) | Attendees are the *other* participants |
| Distribution lists are not attendees | `engineering@` is not a person |
| `timezone` is an IANA name, never an offset | `+05:00` cannot express DST |
| Meeting fixtures need title, start, end, timezone | A partly-specified label caps the achievable score |
| Non-meeting fixtures carry no event data | Otherwise scoring them is meaningless |
| `start_utc >= now_utc` | A meeting before its own grounding time is a mislabel |

`is_meeting` means **"this message should produce a calendar event"** — not "this message mentions a meeting". A cancellation mentions one and must not create anything.

### Known gaps

- **Base rate is wrong on purpose.** 64% of fixtures are meetings; a real inbox is nearer 5%. Balanced sampling gives signal on the event fields, but it means `is_meeting` **precision here flatters the real world** — false positives are far likelier at true base rate. Do not quote this precision as a production number.
- **No ambiguous-date case.** "Next Tuesday" sent on a Monday has no defensible single answer; labelling one requires a policy decision (nearest vs following week) that hasn't been made. Add the case *and* the policy together.
- **All synthetic.** Real mail is messier: broken threading, HTML-only bodies, signature blocks, mixed languages. Add real anonymised cases as they surface.
- **Single recipient timezone.** Every fixture assumes `Asia/Karachi`. A travelling user breaks that assumption.
